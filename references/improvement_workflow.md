# Skill改进工作流

本文件用于实际修改一个或多个个人Skill。目标是从可信证据得到最小、可验证、可回滚的改进。

## 1. 确认实际目标

先解析目标Skill路径，不依赖技能显示名猜测。搜索顺序通常为：

1. 用户明确给出的路径；
2. 用户级Codex技能目录；
3. 用户级Agents技能目录；
4. 当前项目的`.codex/skills`或`.agents/skills`。

同名副本必须比较内容哈希、修改时间和当前会话提供的技能路径。用户未指定时，以当前会话实际暴露的路径为候选，并在写入前说明。

## 2. 完整读取指令边界

修改前必须完整读取目标`SKILL.md`。仅当问题涉及对应模块时读取其直接引用的reference、script、asset模板或`agents/openai.yaml`；不要为了“全面”一次性加载无关大文件。

检查：

- frontmatter名称与description是否准确区分触发场景；
- 正文是否存在互斥规则、重复事实源和失效阶段；
- 相对链接是否存在；
- 脚本调用和参数是否与实际文件一致；
- `openai.yaml`显示名称、介绍、默认提示和隐式调用策略是否一致；
- `VERSION`与正文版本是否一致；
- 是否绑定旧电脑绝对路径、临时文件或不存在的外部工具。

## 3. 将反馈转成可测试规则

用户反馈先改写成三部分：

- **条件**：什么输入或状态下生效；
- **行为**：模型或脚本必须做什么；
- **验收**：如何观察是否正确。

避免把单个项目中的人名、剧情、文件名、比例或平台参数写成全局规则，除非用户明确要求成为长期偏好。

## 4. 补丁选择

按优先顺序选择最小位置：

1. 触发错误：修改frontmatter description或调用政策；
2. 共用决策错误：修改`SKILL.md`；
3. 单一条件分支：修改对应reference；
4. 重复确定性操作错误：修改script并增加脚本测试；
5. 只影响输出模板：修改asset或模板reference。

删除旧规则时同时删除它的解释、示例和失效引用。不要在文件末尾堆叠“新增规则”而保留冲突正文。

## 5. 备份与应用

备份目录必须位于Skill发现路径之外，例如：

```text
<用户Codex目录>/skill-backups/<skill-name>/<YYYYMMDD-HHMMSS>/
```

写入前验证：目标绝对路径位于用户确认的Skill目录内；备份目标不存在；文件清单与源目录对应。保留权限和二进制资源。避免对整个Skill根目录执行递归删除或移动。

使用局部补丁修改文本。格式化或批量机械重写可以使用受控脚本，但修改后必须检查差异，避免覆盖用户同期变更。

## 6. 验证与发布

至少完成：

- frontmatter、名称、引用文件和占位符校验；
- 目标失败用例从失败变为通过；
- 一个相邻的负向触发用例仍不调用该Skill；
- 与修改区域有关的历史行为不退化；
- 新增或修改脚本可执行并有清晰失败信息；
- 不增加新的绝对路径、未声明依赖或越权动作。

新版本只有全部必需测试通过后才生效。若环境缺少测试依赖，明确标记“结构验证通过、行为验证未完成”，不得说已全面通过。

## 7. 学习记录

只有用户要求长期保留该经验，或该案例对防回归确有价值时，才在目标Skill中新增小型评估用例或维护记录。记录事实和验收，不保存无关对话、隐私信息、密钥、Cookie或大段原始日志。

一次修改完成后，告诉用户现有个人Skill整合包是否已过期；没有明确要求时不自动重打包。
