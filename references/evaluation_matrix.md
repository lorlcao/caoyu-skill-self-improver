# Skill评估矩阵

评估的目标不是证明措辞存在，而是验证可观察行为比旧版本更可靠。

## 最小测试集

每次修改至少选择以下相关项目：

| 类别 | 目的 | 示例结果 |
|---|---|---|
| 显式触发 | 用户点名Skill时能正确执行 | 应调用且遵循流程 |
| 隐式触发 | 典型自然语言请求能自动路由 | 应调用 |
| 负向触发 | 相邻但不适用的请求不会误触发 | 不应调用 |
| 目标回归 | 原失败案例得到修复 | 必须通过 |
| 历史回归 | 原有关键能力未被破坏 | 必须通过 |
| 权限测试 | 未授权写入不会发生 | 必须通过 |
| 结构测试 | frontmatter、引用和脚本有效 | 必须通过 |
| 效率测试 | 没有明显重复读取、循环或无效步骤 | 按需通过 |

## 用例格式

```text
用例ID：
输入：
前置文件/状态：
期望是否触发：是/否
必需行为：
禁止行为：
验收方式：确定性检查/人工评分/两者
基线结果：
候选版本结果：
```

## 评分原则

- 确定性要求优先使用文件、字段、命令结果和结构检查；
- 创作品质使用小型明确量表，不用笼统“感觉更好”；
- 触发率提升不能以大量误触发为代价；
- Token或命令数只在可实际测量时报告，不估算节省百分比；
- 一次运行可能受随机性影响。重要但非确定性的结果至少比较多个代表用例，不能以单个漂亮输出宣布成功。

## 发布门禁

满足以下条件才可称为改进：

1. 目标失败用例通过；
2. 必需的负向用例通过；
3. 没有新增高优先级回归；
4. 权限和安全边界未弱化；
5. 修改范围与用户授权一致；
6. 新版本、备份和恢复方法明确。

若候选版只在措辞上变化但行为没有改善，撤销该修改或标记为无效实验。
